01 / Problem statement

Resources in separate VPCs are isolated by default. The objective was to configure VPC peering, add routes between the two VPC CIDR blocks, set security-group rules, and test communication over the addresses assigned to EC2 instances inside the VPCs.

02 / Environment and implementation
  • Cloud platform: Amazon Web Services (AWS).
  • Region: US East (Ohio), us-east-2.
  • VPC CIDR blocks used in the lab: 28.0.0.0/16 and 28.200.0.0/16.
  • Configured a VPC peering connection and routes between the two VPC CIDR blocks.
  • Configured security-group rules for SSH and ICMP connectivity testing.
  • Used two EC2 instances. During testing, the VPC 1 instance had a public IPv4 address and served as the SSH entry point; the VPC 2 instance had no public IPv4 address and was reached through the VPC 1 instance.
  • VPC 2 subnet name: Name not verified from available evidence.

The lab CIDR blocks used here are not RFC 1918 private IPv4 ranges. The network worked for the captured lab tests, but a production design should use suitable private IPv4 ranges and undergo a security review.

03 / Target architecture

The supplied architecture diagram describes the intended/problem target design. It is not an exact representation of the implemented lab: the workbook design uses a separate bastion and two application instances, while the captured setup used two EC2 instances.

04 / Connectivity tests and learning

The report records successful forward and reverse ping sessions: each successful test received four replies with 0% packet loss. Separate screenshots record an initial ping failure with 100% packet loss and a later successful recovery.

The available screenshots do not establish the cause of the failure, so this page does not attribute it to a specific route, security-group change, or firewall setting. The report also records cleanup of the project VPC resources after testing; the former peering connection should not be assumed to be active now.

What I learned

  • How VPC peering, CIDR blocks, and route tables work together.
  • Why security-group rules must allow the traffic being tested.
  • How to test connectivity in both directions and reach an instance without a public IPv4 address through a proxy/bastion instance.
  • Why documenting failed tests and cleaning up lab resources matters.
